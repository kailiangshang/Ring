# Ring 权限模型

## 0. 层级权限架构

Ring 采用层级权限管理机制。创建者对资源拥有完全权限，邀请进来的人需要在邀请时配置具体权限。Session 同理。

```
层级 1: Ring Hub（用户级）
  → 用户对自己机器上的所有资源拥有完全访问权
  → Super Ring 不受 Ring 角色权限限制，可只读访问本机所有 Ring 内容

层级 2: Ring（群组级）
  → Ring 创建者拥有完全权限
  → 邀请成员时，创建者配置成员权限（角色 + 具体操作权限）
  → 成员权限可在后续调整

层级 3: Session（讨论级）
  → Session 创建者拥有 session 完全权限
  → 但：创建 Session 本身需要 Ring 内的权限
  → 邀请 Ring 成员加入 session
```

### 0.1 三层 AI 权限概览

| AI 层级 | 数据访问 | 写入能力 | 触发场景 |
|---------|---------|---------|---------|
| Super Ring（Hub 级） | 不受 Ring 角色限制，按需只读本机所有 Ring 内容 | 无（只读不写） | Ring Hub 页面 |
| Group Ring（Ring 级） | 读写本 Ring 图谱和归档 | 图谱操作 + 归档 + Git | 进入 Ring 空间后默认激活 |
| Session Ring（Session 级） | 继承 Group Ring 数据（只读） | 无（归档操作由 session owner 触发） | 多人 Session 激活时 |

## 1. 角色定义

| 角色 | 描述 | 来源 |
|------|------|------|
| 创建者 | Ring 的创建人，拥有最高权限 | 创建 Ring 时自动获得 |
| 管理员 | 由创建者指定的协管者 | 创建者手动指定 |
| 成员 | 被邀请加入 Ring 的团队成员 | 通过邀请链接加入 |
| 只读 | 只能查看内容的旁观者 | 创建者/管理员手动设置 |

## 2. 权限矩阵

| 操作 | 创建者 | 管理员 | 成员 | 只读 |
|------|--------|--------|------|------|
| 查看 Ring 信息 | ✅ | ✅ | ✅ | ✅ |
| 查看图谱和归档内容 | ✅ | ✅ | ✅ | ✅ |
| 和 Group Ring 对话 | ✅ | ✅ | ✅ | ❌ |
| 使用工具（会议归档/学习中心/深度调研） | ✅ | ✅ | ✅ | ❌ |
| Export 对话内容 | ✅ | ✅ | ✅ | ❌ |
| 手动归档（直接 commit） | ✅ | ✅ | ❌ | ❌ |
| 提交 PR（归档请求） | ✅ | ✅ | ✅ | ❌ |
| 审核 PR（合并/拒绝） | ✅ | ✅ | ❌ | ❌ |
| 查看其他成员的 PR | ✅ | ✅ | 仅自己的 | ❌ |
| 创建 Session（多人讨论） | ✅ | ✅ | 需创建者授权 | ❌ |
| 管理 Ring 成员（邀请/移除/角色调整） | ✅ | ❌ | ❌ | ❌ |
| 编辑 .ring/role.md 和 .ring/conventions.md | ✅ | ✅ | ❌ | ❌ |
| 修改蓝图模板 | ✅ | ❌ | ❌ | ❌ |

> **创建 Session 权限**：创建者和管理员可直接创建 Session；普通成员需要创建者预先授权。授权为永久授权（一直有效，直到创建者主动撤销）。被授权成员可以创建和关闭 Session，一次只能有一个活跃 Session。

> **PR 审核队列**：成员提交归档 PR 后进入串行审核队列，逐个审核避免 graph.json 冲突。冲突时打回给提交成员（关闭 MR + 通知），成员 pull 最新后重新提交。

> **.ring/ 写入权限**：`.ring/` 目录下所有文档（包括 role.md、conventions.md 及 AI 自动维护的 4 个文档），只有创建者和管理员可以写入（直接 commit）。成员完全只读，不可编辑不可 PR。成员想修改约定 → 向创建者/管理员提出。

## 3. 交互模式

权限通过三种交互模式控制，决定 Group Ring 的自主权。

### 3.1 日常对话模式

| 属性 | 值 |
|------|---|
| 触发方式 | 进入 Ring 后默认状态 |
| AI 权限 | 只读 — 可查询图谱和归档内容 |
| 允许操作 | 问答、聊天、调用工具查看结果 |
| 禁止操作 | 修改图谱、创建节点、Git 操作 |
| Git 操作 | 无 |
| 额外能力 | 可点击 export 按钮触发归档流程 |

### 3.2 手动归档模式

| 属性 | 值 |
|------|---|
| 触发方式 | 用户说"归档"/"保存"/"记录到图谱"，或点击 export 按钮，或 AI 主动推荐 |
| AI 权限 | 推荐 — 可分析内容并推荐图谱操作 |
| 允许操作 | AI 推荐节点位置，用户确认后执行 |
| 确认要求 | 每个图谱操作都需要用户明确确认 |
| Git 操作 | 创建者/管理员：直接 commit；成员：提交 PR |

### 3.3 Auto 模式

| 属性 | 值 |
|------|---|
| 触发方式 | 用户点击"Auto"按钮 |
| AI 权限 | 完全开放 — 读写图谱、生成 Markdown |
| 允许操作 | AI 自主判断内容是否值得归档并自动执行 |
| 确认要求 | 不需要用户逐个确认 |
| Git 操作（创建者/管理员） | AI 自动 commit |
| Git 操作（普通成员） | 批量标记推荐内容，用户一次性确认后合并成一个 PR |
| 退出方式 | 用户再次点击"Auto"按钮退出 |

## 4. 邀请机制

### 4.1 两种邀请链接

| 类型 | 加入方式 | token_id 分配 | 使用场景 |
|------|---------|-------------|---------|
| 开放链接（open） | 点链接直接加入 | 自动递增分配 | 团队内部快速拉人 |
| 审核链接（audit） | 点链接 → 提交申请 → 创建者审批 | 审批通过后分配 | 需要确认身份的邀请 |

### 4.2 Token 规则

- Token 为一次性或多次（`max_uses`，开放链接可设为 0 表示不限）
- 格式：`base64url(random 32 bytes)`，不可猜测
- 默认有效期 24 小时，创建者可自定义
- 创建者可撤销未使用的 token（设置 `revoked_at`）
- 创建者可批量生成多个 token 分发给不同人
- 可选设 `max_members`（Ring 最大人数上限，防止链接泄露）

### 4.3 生成邀请

1. 创建者在 Ring 空间点击"邀请"按钮
2. 选择链接类型（开放 / 审核）
3. 配置参数（角色、有效期、最大使用次数、最大人数）
4. 系统生成邀请链接：`http://{创建者内网IP}:7420/ring/join?token=xxx`
5. 创建者通过公司通讯工具发送链接

### 4.4 加入流程（开放链接）

1. 被邀请人点击链接
2. 引导页检测本地 Ring 后端
3. 未安装 → 显示安装指引 → 安装后点击"继续加入" → 跳转本地 join URL
4. 已安装或跳转后 → 本地后端检查 Setup 状态
5. 未 Setup → 先走 Setup（display_name + LLM + GitLab）→ 完成后自动 join
6. 已 Setup → 直接 join
7. 输入 display_name → clone 仓库 → 分配 token_id → 加入 Ring

### 4.5 加入流程（审核链接）

1. 被邀请人点击链接 → 看到 Ring 名称 + 成员列表
2. 输入 display_name + 申请理由
3. 创建者收到通知 → 审批
4. 批准 → 分配 token_id → clone 仓库 → 通知申请人
5. 拒绝 → 通知申请人（附理由）

### 4.6 角色变更

- 创建者可将成员提升为管理员
- 创建者可将管理员降级为成员
- 创建者可将成员设为只读
- 创建者可移除成员
- 管理员不能变更角色

## 5. Session 级权限

> Session 是 Ring 内的多人实时讨论会话。Session 有独立的权限控制，与 Ring 级权限正交。

### 5.1 Session 角色

| 角色 | 描述 | 来源 |
|------|------|------|
| Session Owner | Session 创建者，拥有 session 管理权限 | 创建 Session 时自动获得 |
| Participant | Session 参与者，可收发消息和查看 AI 回复 | 被 session owner 邀请 |

### 5.2 Session 权限矩阵

| 操作 | Session Owner | Participant | 只读成员（旁听者） |
|------|--------------|-------------|-----------------|
| 查看消息和 AI 回复 | ✅ | ✅ | ✅ |
| 发送消息 | ✅ | ✅ | ❌ |
| 邀请其他 Ring 成员加入 session | ✅ | ❌ | ❌ |
| 移除 participant | ✅ | ❌ | ❌ |
| 开关归档能力 | ✅ | ❌ | ❌ |
| 触发归档操作（需归档已开启） | ✅ | ❌ | ❌ |
| 关闭 session | ✅ | ❌ | ❌ |
| 重新打开已关闭的 session | ✅ | ❌ | ❌ |
| 删除 session | ✅ | ❌ | ❌ |
| 主动离开 session | ✅ | ✅ | ✅ |

### 5.3 Session 鉴权

- **加入鉴权**：被邀请者必须是 Ring 的已有成员（任意角色），由创建者后端验证
- **WebSocket 连接鉴权**：连接 session WebSocket 频道时需提供 Ring 成员身份 token
- **归档鉴权**：session 归档操作走 Ring 内角色权限（创建者/管理员直接 commit，成员提交 PR）

### 5.4 Session 与 Ring 权限关系

```
Ring 级权限
├── 决定：能否进入 Ring 空间
├── 决定：能否创建 Session（创建者/管理员可创建，成员需授权）
├── 决定：归档时的 Git 操作权限（直接 commit vs 提交 PR）
├── 决定：能否被邀请进 Session（必须是 Ring 成员）
└── 决定：成员被移除时的 Session 处理

Session 级权限
├── 决定：session 内的管理操作（invite/close/delete）
├── 决定：谁能触发归档（仅 session owner）
└── 决定：归档开关（仅 session owner）
```

### 5.5 成员移除时的 Session 处理

当 Ring 创建者移除一个成员时，需处理该成员参与的活跃 Session：

| 被移除者在 Session 中的角色 | 处理方式 |
|--------------------------|---------|
| Session Owner | 创建者必须先指定继承者（转移 session ownership），才能移除该成员 |
| Participant | 保留该成员的所有历史消息，通过 WebSocket 踢出 session（`session_member_kicked`），该成员立即无法继续发送消息 |

### 5.6 Session 暂停机制

当 Session owner 离线时：

- 后端推送 `session_paused` 事件给所有参与者
- 所有参与者无法发消息，Session 暂停
- Session owner 重连后推送 `session_resumed` 事件
- 所有参与者可继续发消息
- **不设临时接管机制**：消息始终存储在 Session owner 后端的 SQLite 中，避免多端消息合并复杂度
