# Ring 产品需求文档（PRD）

## 1. 产品概述

### 1.1 产品定位

Ring 是一个面向公司内网的群组知识协作空间。以 Ring（群组空间）为核心入口，知识图谱为骨架，Markdown 为内容载体，Git 为协作机制，AI 为群组组长。

### 1.2 目标用户

公司内网环境下的团队和项目组，需要：
- 沉淀团队知识（会议决策、调研报告、学习笔记）
- 协作管理知识资产（版本控制、审核机制）
- AI 辅助知识整理和洞察

### 1.3 核心价值

| 维度 | 描述 |
|------|------|
| 本地优先 | 数据存储在用户本地，不依赖中心服务器 |
| 隐私保护 | 敏感信息脱敏，LLM 可配置 |
| 群组协作 | 多人知识空间，Git-like 协作机制 |
| 知识图谱 | 结构化知识表示，可视化导航 |
| 三层 AI | Super Ring（全局）/ Group Ring（群组）/ Session Ring（讨论场景）|
| 自成长 | AI prompt 驱动场景适配，Ring 做通用框架而非硬编码功能 |

### 1.4 自成长设计理念

Ring 不为特定角色（行政/技术/管理）硬编码功能，而是通过三层机制实现场景自适应：

**1. AI prompt 是角色适配层**
- Group Ring 的 system prompt 决定它的行为模式
- 行政 Ring："你是行政助理，擅长会议纪要和制度管理"
- 技术 Ring："你是技术组长，擅长架构决策记录"
- 同一个 Ring 框架，不同 prompt = 不同角色

**2. 蓝图是知识结构适配层**
- 图谱结构由用户和 Group Ring 在蓝图阶段共创
- 不是我们预设"会议纪要模板"，而是 AI 根据用户描述生成匹配的图谱结构
- 蓝图模板可复用、可分享

**3. 行为反馈是持续优化层**
- 用户修正 Group Ring 的归档推荐（粒度、位置、更新 vs 新建）→ AI 从反馈中学习
- 不同 Ring 的 Group Ring 实例独立进化，不互相干扰

### 1.4 产品定位转变

| 维度 | 之前（SigeNoteBook） | 现在（Ring） |
|------|---------------------|-------------|
| 定位 | 本地优先的个人知识工作台 | 公司内网的群组知识协作空间 |
| 入口 | 6 个功能模块 | Ring Hub（群组空间列表） |
| 数据组织 | 分类存储（SQLite） | 知识图谱（骨架）+ Markdown（血肉） |
| 协作方式 | 完全单机 | Git-like 多人协作（通过 GitLab） |

## 2. 核心功能需求

### 2.1 Ring Hub（首页）

**描述**：Ring Hub 是整个产品的入口，展示用户参与的所有 Ring。

**功能点**：
- Ring 列表展示（卡片形式，显示 Ring 名称、成员数、最近活动时间、图谱节点数）
- 创建 Ring（填写名称 + Group Ring 角色描述 → 初始化 `.ring/role.md`）
- Super Ring 入口（全局助手）
- 全局设置（LLM 配置、隐私过滤规则）
- UI 提示："对话记录仅保存在当前设备"（对话数据不跨设备同步）

### 2.2 Ring 空间

**描述**：进入某个 Ring 后的主工作区域。

**功能点**：
- 顶部导航栏：Ring 名称、成员头像列表、邀请按钮
- 左侧图谱导航：节点树，点击跳转对应 Markdown 内容
- 中央主区域（可切换视图）：
  - 对话视图（默认）：和 Group Ring 交互
  - 图谱视图：D3.js 可视化，节点可拖拽
  - 归档视图：Markdown 文件列表 + PR 队列 + Git Diff 查看
- 工具栏（底部或侧边）：预设工作流入口 + 未来扩展

### 2.3 知识图谱

**描述**：Ring 的知识骨架，支持蓝图构建和自然生长。

**蓝图构建阶段**：
- 创建 Ring 后进入蓝图构建页面
- **两条路径**：
  - **快速路径**：用户直接选择预设模板 → 预览图谱结构（节点+边可视化）→ "使用此模板" → 确认蓝图（一步到位）
  - **深度路径**：用户点"自定义"或"从零开始" → Group Ring 通过不限轮数的对话，和用户反复确认图谱结构
- 确定需要的图谱数量（默认上限 3 个，过高提醒资源消耗）
- 确定每个图谱的主题和顶层分类
- 提供可视化预览，用户明确点击"确认蓝图"后建立

**后续生长阶段**：
- 对话中产生新内容 → AI 匹配蓝图大类 → 建议子节点或归入现有节点
- 取决于权限模式：手动归档需确认，Auto 模式自动执行

**多图谱规则**：
- 每个 Ring 可维护多个独立图谱
- 每个图谱有独立的 graph.json 和节点树
- 图谱之间没有显式跨图谱边
- 同一个 Markdown 文件可被多个图谱的不同节点引用（隐式关联）

**修正机制**：
- 在对话中指示 Group Ring 修正（"删除刚才那个节点"）
- 在归档视图的 Git 历史中 revert
- 图谱可视化支持展开/折叠节点，但不支持直接编辑

### 2.4 归档机制

**归档触发**：
- 用户在对话中手动标记内容为"值得归档"（说"归档"或点击 export 按钮）
- 工具产出后 AI 主动推荐"是否归档到图谱"
- Auto 模式下 AI 自动判断并归档

**归档形式**：
- 所有内容统一转为 Markdown 文件
- 二进制文件（图片、PDF）存路径引用，不进 Git
- 每个 Markdown 对应图谱的一个节点

**归档操作流程**：
```
标记归档
  → 后端自动 git pull（确保本地图谱状态最新）
  → AI 推荐挂载到图谱哪个节点（或建议新建节点）
  → 用户确认节点位置（手动归档模式）/ AI 自动执行（Auto 模式）
  → 生成 Markdown 文件 + 更新 graph.json
  → 创建者/管理员：直接 commit + push
  → 普通成员：提交 PR → 创建者在 Ring 内审核合并
```

**PR 审核队列**：
- 成员提交归档 PR 后进入审核队列，前端显示队列状态（当前正在审核 + 排队数量）
- PR 逐个审核（串行队列），避免 graph.json 合并冲突
- 如果 PR 与已合并内容冲突 → 打回给提交成员（关闭 MR + 通知）→ 成员 pull 最新后重新提交

### 2.5 Git 集成（GitLab）

**仓库结构**：
- 每个 Ring（Group Ring）一个独立 GitLab 仓库
- 用户可创建/加入多个 Ring，本地管理多个仓库
- 用户身份通过本地 `.ring-local/identity.json` 管理（不进 Git，跨设备时重新 Setup）

**Git 操作在 Ring 内完成**：
- 创建者/管理员直接归档 → 后端自动 commit + push
- 成员提交归档 → 后端创建分支 + commit + push + GitLab API 创建 MR（进入审核队列）
- 创建者审核 PR → 在 Ring 内查看 Diff、合并/拒绝（冲突时打回）
- 成员加入时 → 自动从 GitLab clone 仓库到本地

**Git 仓库结构**：
```
ring-{name}/
├── .ring-local/            # .gitignore 排除，纯本地
│   └── identity.json       # 当前用户身份（不进 Git）
├── blueprint.json
├── .ring/                  # AI 上下文文档（进 Git）
├── graphs/
├── nodes/
└── assets/
```

### 2.6 三层 AI 架构

Ring 的 AI 系统分为三个层级，严格分层，各自独立运行：

| 层级 | 名称 | 定位 | 触发场景 | 数据访问 |
|------|------|------|---------|---------|
| Hub 级 | **Super Ring** | 全局助手 + 跨 Ring 协调者 | Ring Hub 页面 | 按需只读本机所有 Ring 内容 |
| Ring 级 | **Group Ring** | 群组专属 AI | 进入 Ring 空间后默认激活 | 读写本 Ring 图谱和归档 |
| Session 级 | **Session Ring** | 多人讨论场景 AI | 创建多人 Session 时激活 | 继承 Group Ring 数据（只读） |

**Super Ring（Hub 级）**：
- Ring Hub 全局助手，负责使用引导、Ring 创建配置
- 跨 Ring 能力：分析多个 Ring 的数据、跨 Ring 问答、汇总总结、合并推荐
- 按需读取 Ring 内容（图谱 + 归档 Markdown），只读不写
- 合并推荐只生成建议，合并操作由用户在具体 Ring 中执行

**Group Ring（Ring 级）**：
- 群组专属 AI，每个 Ring 一个实例
- 单人对话时默认激活（不需要 Session）
- 负责图谱操作、归档管理、内容问答、工具调用
- **行为由 `.ring/` 文档体系驱动**（6 个持久化 MD 文档，随 Git 版本管理，可长期进化）
- `.ring/` 只有创建者和管理员可写入（直接 commit），成员完全只读
- `.ring/role.md`（角色定义）+ `.ring/conventions.md`（团队约定）由创建者/管理员编辑
- `.ring/archive-patterns.md`（归档偏好）+ `.ring/corrections.md`（修正记录）由 AI 自动积累
- `.ring/knowledge-summary.md`（知识总结）由 AI 定期生成
- `.ring/active-context.md`（活跃上下文）由 AI 动态维护
- 按需加载策略：核心层（role + conventions + active-context）始终加载，扩展层按场景加载

**Session Ring（Session 级）**：
- 仅在多人 Session 激活时存在
- **必须以预设场景启动**，当前支持：
  - `deep_research`（深度调研）：跨源聚合 + 报告生成
  - `meeting_archive`（会议归档）：结构化提取 + 归档推荐
  - `learning_center`（学习中心）：知识解读 + 概念提取
- 不开放自定义逻辑，保留扩展能力
- 所有 session 成员共享，回复广播
- Session 关闭后实例销毁

**层级调用规则**：
- 三层之间无直接函数调用
- Super Ring 可向下只读查询 Group Ring 的数据
- 通过共享数据层（SQLite + petgraph 内存图 + Git）间接交互

### 2.7 预设工作流

保留三个基础工具作为预设工作流，未来可扩展：

| 工具 | 原子能力组合 | 使用方式 |
|------|------------|---------|
| 会议归档 | 文件解析 + 文本清洗 + 结构化提取 + Markdown 生成 | 对话中上传会议记录 → AI 提取关键信息 → 推荐挂载到图谱节点 |
| 学习中心 | PDF 解析 + 知识图谱生成 + 文档解读 | 上传 PDF → AI 生成解读 + 提取概念 → 推荐创建/更新图谱节点 |
| 深度调研 | 本地检索 + 网页爬取 + 报告生成 | 对话中说"调研 XX 主题" → AI 聚合资源 → 生成报告 Markdown → 挂载到图谱 |

### 2.9 导出中心

**描述**：Ring 提供完整的导出能力，支持多种格式输出。

**导出选项**：

| # | 导出类型 | 格式 | 描述 |
|---|---------|------|------|
| 1 | 图谱图片 | PNG / SVG / PDF | 将 D3.js 图谱导出为静态图片 |
| 2 | 单篇 Markdown | .md | 导出某个节点的 Markdown 文件 |
| 3 | 对话记录 | Markdown / PDF | 导出完整对话历史 |
| 4 | AI 结构化报告 | Markdown / PDF | AI 基于指定节点内容生成结构化报告 |
| 5 | Session 讨论记录 | Markdown / PDF | 导出多人讨论的完整记录 |
| 6 | 整 Ring 数据备份 | .tar.gz | 完整备份（graph.json + Markdown + 元数据 + assets） |
| 7 | graph.json 原始数据 | JSON | 导出图谱的 JSON 原始数据 |

**可视化**：
- 图谱视图为静态查看模式（D3.js 力导向图渲染）
- 支持缩放、平移、节点高亮
- 支持展开/折叠节点（查看或隐藏子节点）
- 不支持在可视化界面上直接编辑节点属性

**权限**：
- Ring 成员及以上角色可使用导出功能
- 只读角色可导出图谱图片和 graph.json（只读数据）

### 2.10 对话上下文管理

**描述**：管理 Group Ring 对话的 LLM token 消耗，防止上下文溢出。

**两种会话模式**：
- **storage（持久会话）**：消息存入 SQLite，支持历史回溯、归档、compact。默认模式
- **ephemeral（临时会话）**：消息仅存内存，关闭对话后丢失。适合快速问答

**Token 管理（仅 storage 模式）**：
- 系统追踪每个会话的累计 LLM token 消耗
- 超过阈值（默认 100k tokens，可配置）时提醒用户执行 compact
- 用户可开启 `auto_compact`：达到阈值自动触发 compact，无需手动操作
- **Compact 行为**：Group Ring 将历史对话压缩为摘要（summary），替换原始消息作为上下文输入。前端展示"正在压缩对话上下文..."提示。原始消息仍保留在 messages 表中供历史回溯，但不再喂给 LLM

### 2.11 通知系统

**描述**：Ring 内的事件通知机制。

**通知来源**：
- PR 状态变更（新 PR、合并、拒绝）
- 成员变更（新成员加入、角色调整、成员移除）
- Session 邀请

**推送方式**：
- 在线用户：WebSocket 实时推送
- 离线用户：通知缓存到本地 SQLite（`notifications` 表），下次启动前端展示未读通知列表

### 2.12 Ring 生命周期

- **active**：正常运行（Ring 创建后始终为 active，无归档冻结机制）
- Ring 的内容归档（对话→图谱节点+Markdown+Git commit）是持续性操作，不冻结 Ring 本身

### 2.7 Session 多人讨论

**描述**：Ring 内的多人实时讨论空间，区别于 Ring 级的仓库同步邀请。

**两层邀请机制**：

| 层级 | 目的 | 邀请范围 | 鉴权方式 | 数据同步 |
|------|------|---------|---------|---------|
| Ring 级 | 加入 Ring，获得仓库完整数据 | 任何人（通过 token） | API Key + invite token | Git clone/push/pull |
| Session 级 | 加入具体讨论，实时协作 | 仅 Ring 内已有成员 | Ring 成员身份验证 | 创建者后端 WebSocket 中转 |

**功能点**：
- Ring 内有权限的成员可创建 Session 并邀请其他 Ring 成员
- **同一个 Ring 同一时刻只能有一个活跃 Session**
- 创建 Session 必须选择预设场景（决定 Session Ring 的行为）：
  - `discussion`（自由讨论）：多人自由聊天，Session Ring 作为基础讨论助手
  - `deep_research`（深度调研）：跨源聚合 + 报告生成
  - `meeting_archive`（会议归档）：结构化提取 + 归档推荐
  - `learning_center`（学习中心）：知识解读 + 概念提取
- 所有参与者共享一个 Group Ring 实例，AI 回复对所有人可见
- 消息通过创建者后端 WebSocket hub 中转（不经过 GitLab）
- Session owner 离线时 Session 暂停，参与者无法发消息；owner 重连后自动恢复
- 离线成员重连后自动补发缺失消息（基于 seq_num）
- Session owner 可动态开关归档能力
- 归档开启后，仅 session owner 可触发归档操作（走 Ring 标准归档流程）
- Session 生命周期由 session owner 管理（关闭/删除/重新打开）
- 关闭的 session 保留聊天记录在创建者后端 SQLite，可随时重新打开

## 3. 非功能需求

### 3.1 性能

- 图谱渲染支持 100+ 节点不卡顿
- Git 操作（commit/push/pull）在 10 秒内完成
- AI 响应采用流式输出

### 3.2 安全

- Git 凭证加密存储
- 敏感信息隐私过滤（可配置规则）
- LLM API Key 本地加密存储

### 3.3 可用性

- 创建者机器在线时 Ring 可完整使用
- 成员本地有 Git 仓库克隆，可离线查看归档内容
- 新用户引导流程（Super Ring 辅助）
- **通知系统**：PR 状态变更、成员变更等通过 WebSocket 实时推送。用户离线时通知缓存到 SQLite，下次启动展示未读通知列表
- **Session 暂停机制**：Session owner 离线时 Session 暂停，所有参与者无法发消息。Owner 重连后自动恢复

### 3.4 可扩展性

- 工作流系统预留扩展能力（当前不开放自定义）
- 工具栏预留第三方工具接入空间
- 图谱模板支持用户自定义

## 4. 角色权限

| 角色 | 权限 |
|------|------|
| 创建者 | 直接 commit、审核 PR、管理成员、编辑 .ring/ 文档、管理蓝图模板、分配 token_id |
| 管理员（可指定） | 直接 commit、审核 PR、编辑 .ring/ 文档 |
| 成员 | 对话、使用工具、提交 PR（归档请求，进入审核队列）、export 对话内容 |
| 只读 | 查看图谱和归档内容，不能对话和提交 |

**邀请机制**：创建者生成邀请链接，支持两种类型：
- **开放链接**：`http://{创建者内网IP}:7420/ring/join?token=xxx`，点链接直接加入，自动分配 token_id
- **审核链接**：被邀请人提交申请（输入 display_name）→ 创建者审批 → 通过后分配 token_id 并加入
- 加入时同步 Ring 内其他成员的名称列表

## 5. 约束与假设

### 约束

- 网络环境：公司内网，每人有固定内网 IP + 开放端口
- 大模型调用：通过云端 API（OpenAI / Anthropic / Ollama）
- 版本管理：使用公司内部 GitLab
- 前端框架：React + TypeScript
- 后端框架：Rust + Axum

### 假设

- 创建者机器在线时 Ring 才可完整使用
- 成员浏览器可直接访问创建者内网 IP
- 公司 GitLab 可通过内网访问
