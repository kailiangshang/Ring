## 1. 产品概述

### 1.1 产品定位

Ring 是一个面向公司内网的群组知识协作空间。以 Ring（群组空间）为核心入口，知识图谱为骨架，Markdown 为内容载体，Git 为协作机制，AI 为群组组长。

### 1.2 目标用户

公司内网环境下的团队和项目组，需要：
- 沉淀团队知识（会议决策、调研报告、学习笔记）
- 协作管理知识资产（版本控制、审核机制）
- AI 辅助知识整理和洞察

### 1.3 核心价值

| 维度 | 描述 |
|------|------|
| 本地优先 | 数据存储在用户本地，不依赖中心服务器 |
| 隐私保护 | 敏感信息脱敏，LLM 可配置 |
| 群组协作 | 多人知识空间，Git-like 协作机制 |
| 知识图谱 | 结构化知识表示，可视化导航 |
| 三层 AI | Super Ring（全局）/ Group Ring（群组）/ Session Ring（讨论场景）|
| 自成长 | AI prompt 驱动场景适配，Ring 做通用框架而非硬编码功能 |

### 1.4 自成长设计理念

Ring 不为特定角色（行政/技术/管理）硬编码功能，而是通过三层机制实现场景自适应：

**1. AI prompt 是角色适配层**
- Group Ring 的 system prompt 决定它的行为模式
- 行政 Ring："你是行政助理，擅长会议纪要和制度管理"
- 技术 Ring："你是技术组长，擅长架构决策记录"
- 同一个 Ring 框架，不同 prompt = 不同角色

**2. 蓝图是知识结构适配层**
- 图谱结构由用户和 Group Ring 在蓝图阶段共创
- 不是我们预设"会议纪要模板"，而是 AI 根据用户描述生成匹配的图谱结构
- 蓝图模板可复用、可分享

**3. 行为反馈是持续优化层**
- 用户修正 Group Ring 的归档推荐（粒度、位置、更新 vs 新建）→ AI 从反馈中学习
- 不同 Ring 的 Group Ring 实例独立进化，不互相干扰

### 1.5 产品定位转变

| 维度 | 之前（SigeNoteBook） | 现在（Ring） |
|------|---------------------|-------------|
| 定位 | 本地优先的个人知识工作台 | 公司内网的群组知识协作空间 |
| 入口 | 6 个功能模块 | Ring Hub（群组空间列表） |
| 数据组织 | 分类存储（SQLite） | 知识图谱（骨架）+ Markdown（血肉） |
| 协作方式 | 完全单机 | Git-like 多人协作（通过 GitLab） |

## 2. 核心功能需求

### 2.1 Ring Hub（首页）

**描述**：Ring Hub 是整个产品的入口，展示用户参与的所有 Ring。

**功能点**：
- Ring 列表展示（卡片形式，显示 Ring 名称、成员数、最近活动时间、图谱节点数）
- 创建 Ring（填写名称 + Group Ring 角色描述 → 初始化 `.ring/role.md`）
- Super Ring 入口（全局助手）
- 全局设置（LLM 配置、隐私过滤规则）
- UI 提示："对话记录仅保存在当前设备"（对话数据不跨设备同步）

### 2.2 Ring 空间

**描述**：进入某个 Ring 后的主工作区域。

**功能点**：
- 顶部导航栏：Ring 名称、成员头像列表、邀请按钮
- 左侧图谱导航：节点树，点击跳转对应 Markdown 内容
- 中央主区域（可切换视图）：
  - 对话视图（默认）：和 Group Ring 交互
  - 图谱视图：D3.js 可视化，节点可拖拽
  - 归档视图：Markdown 文件列表 + PR 队列 + Git Diff 查看
- 工具栏（底部或侧边）：预设工作流入口 + 未来扩展

### 2.3 知识图谱

**描述**：Ring 的知识骨架，支持蓝图构建和自然生长。

**蓝图构建阶段**：
- 创建 Ring 后进入蓝图构建页面
- **两条路径**：
  - **快速路径**：用户直接选择预设模板 → 预览图谱结构（节点+边可视化）→ "使用此模板" → 确认蓝图（一步到位）
  - **深度路径**：用户点"自定义"或"从零开始" → Group Ring 通过不限轮数的对话，和用户反复确认图谱结构
- 确定需要的图谱数量（默认上限 3 个，过高提醒资源消耗）
- 确定每个图谱的主题和顶层分类
- 提供可视化预览，用户明确点击"确认蓝图"后建立

**后续生长阶段**：
- 对话中产生新内容 → AI 匹配蓝图大类 → 建议子节点或归入现有节点
- 取决于权限模式：手动归档需确认，Auto 模式自动执行

**多图谱规则**：
- 每个 Ring 可维护多个独立图谱
- 每个图谱有独立的 graph.json 和节点树
- 图谱之间没有显式跨图谱边
- 同一个 Markdown 文件可被多个图谱的不同节点引用（隐式关联）

**修正机制**：
- 在对话中指示 Group Ring 修正（"删除刚才那个节点"）
- 在归档视图的 Git 历史中 revert
- 图谱可视化支持展开/折叠节点，但不支持直接编辑

### 2.4 归档机制

**归档触发**：
- 用户在对话中手动标记内容为"值得归档"（说"归档"或点击 export 按钮）
- 工具产出后 AI 主动推荐"是否归档到图谱"
- Auto 模式下 AI 自动判断并归档

**归档形式**：
- 所有内容统一转为 Markdown 文件
- 二进制文件（图片、PDF）存路径引用，不进 Git
- 每个 Markdown 对应图谱的一个节点

**归档操作流程**：
```
标记归档
  → 后端自动 git pull（确保本地图谱状态最新）
  → AI 推荐挂载到图谱哪个节点（或建议新建节点）
  → 用户确认节点位置（手动归档模式）/ AI 自动执行（Auto 模式）
  → 生成 Markdown 文件 + 更新 graph.json
  → 创建者/管理员：直接 commit + push
  → 普通成员：提交 PR → 创建者在 Ring 内审核合并
```

**PR 审核队列**：
- 成员提交归档 PR 后进入审核队列，前端显示队列状态（当前正在审核 + 排队数量）
- PR 逐个审核（串行队列），避免 graph.json 合并冲突
- 如果 PR 与已合并内容冲突 → 打回给提交成员（关闭 MR + 通知）→ 成员 pull 最新后重新提交

### 2.5 Git 集成（GitLab）

**仓库结构**：
- 每个 Ring（Group Ring）一个独立 GitLab 仓库
- 用户可创建/加入多个 Ring，本地管理多个仓库
- 用户身份通过本地 `.ring-local/identity.json` 管理（不进 Git，跨设备时重新 Setup）

**Git 操作在 Ring 内完成**：
- 创建者/管理员直接归档 → 后端自动 commit + push
- 成员提交归档 → 后端创建分支 + commit + push + GitLab API 创建 MR（进入审核队列）
- 创建者审核 PR → 在 Ring 内查看 Diff、合并/拒绝（冲突时打回）
- 成员加入时 → 自动从 GitLab clone 仓库到本地

**Git 仓库结构**：
```
ring-{name}/
├── .ring-local/            # .gitignore 排除，纯本地
│   └── identity.json       # 当前用户身份（不进 Git）
├── blueprint.json
├── .ring/                  # AI 上下文文档（进 Git）
├── graphs/
├── nodes/
└── assets/
```

### 2.6 三层 AI 架构

Ring 的 AI 系统分为三个层级，严格分层，各自独立运行：

| 层级 | 名称 | 定位 | 触发场景 | 数据访问 |
|------|------|------|---------|---------|
| Hub 级 | **Super Ring** | 全局助手 + 跨 Ring 协调者 | Ring Hub 页面 | 按需只读本机所有 Ring 内容 |
| Ring 级 | **Group Ring** | 群组专属 AI | 进入 Ring 空间后默认激活 | 读写本 Ring 图谱和归档 |
| Session 级 | **Session Ring** | 多人讨论场景 AI | 创建多人 Session 时激活 | 继承 Group Ring 数据（只读） |

**Super Ring（Hub 级）**：
- Ring Hub 全局助手，负责使用引导、Ring 创建配置
- 跨 Ring 能力：分析多个 Ring 的数据、跨 Ring 问答、汇总总结、合并推荐
- 按需读取 Ring 内容（图谱 + 归档 Markdown），只读不写
- 合并推荐只生成建议，合并操作由用户在具体 Ring 中执行

**Group Ring（Ring 级）**：
- 群组专属 AI，每个 Ring 一个实例
- 单人对话时默认激活（不需要 Session）
- 负责图谱操作、归档管理、内容问答、工具调用
- **行为由 `.ring/` 文档体系驱动**（6 个持久化 MD 文档，随 Git 版本管理，可长期进化）
- `.ring/` 只有创建者和管理员可写入（直接 commit），成员完全只读
- `.ring/role.md`（角色定义）+ `.ring/conventions.md`（团队约定）由创建者/管理员编辑
- `.ring/archive-patterns.md`（归档偏好）+ `.ring/corrections.md`（修正记录）由 AI 自动积累
- `.ring/knowledge-summary.md`（知识总结）由 AI 定期生成
- `.ring/active-context.md`（活跃上下文）由 AI 动态维护
- 按需加载策略：核心层（role + conventions + active-context）始终加载，扩展层按场景加载

**Session Ring（Session 级）**：
- 仅在多人 Session 激活时存在
- **必须以预设场景启动**，当前支持：
  - `deep_research`（深度调研）：跨源聚合 + 报告生成
  - `meeting_archive`（会议归档）：结构化提取 + 归档推荐
  - `learning_center`（学习中心）：知识解读 + 概念提取
- 不开放自定义逻辑，保留扩展能力
- 所有 session 成员共享，回复广播
- Session 关闭后实例销毁

**层级调用规则**：
- 三层之间无直接函数调用
- Super Ring 可向下只读查询 Group Ring 的数据
- 通过共享数据层（SQLite + petgraph 内存图 + Git）间接交互

### 2.7 预设工作流

保留三个基础工具作为预设工作流，未来可扩展：

| 工具 | 原子能力组合 | 使用方式 |
|------|------------|---------|
| 会议归档 | 文件解析 + 文本清洗 + 结构化提取 + Markdown 生成 | 对话中上传会议记录 → AI 提取关键信息 → 推荐挂载到图谱节点 |
| 学习中心 | PDF 解析 + 知识图谱生成 + 文档解读 | 上传 PDF → AI 生成解读 + 提取概念 → 推荐创建/更新图谱节点 |
| 深度调研 | 本地检索 + 网页爬取 + 报告生成 | 对话中说"调研 XX 主题" → AI 聚合资源 → 生成报告 Markdown → 挂载到图谱 |

### 2.8 导出中心

**描述**：Ring 提供完整的导出能力，支持多种格式输出。

**导出选项**：

| # | 导出类型 | 格式 | 描述 |
|---|---------|------|------|
| 1 | 图谱图片 | PNG / SVG / PDF | 将 D3.js 图谱导出为静态图片 |
| 2 | 单篇 Markdown | .md | 导出某个节点的 Markdown 文件 |
| 3 | 对话记录 | Markdown / PDF | 导出完整对话历史 |
| 4 | AI 结构化报告 | Markdown / PDF | AI 基于指定节点内容生成结构化报告 |
| 5 | Session 讨论记录 | Markdown / PDF | 导出多人讨论的完整记录 |
| 6 | 整 Ring 数据备份 | .tar.gz | 完整备份（graph.json + Markdown + 元数据 + assets） |
| 7 | graph.json 原始数据 | JSON | 导出图谱的 JSON 原始数据 |

**可视化**：
- 图谱视图为静态查看模式（D3.js 力导向图渲染）
- 支持缩放、平移、节点高亮
- 支持展开/折叠节点（查看或隐藏子节点）
- 不支持在可视化界面上直接编辑节点属性

**权限**：
- Ring 成员及以上角色可使用导出功能
- 只读角色可导出图谱图片和 graph.json（只读数据）

### 2.9 对话上下文管理

**描述**：管理 Group Ring 对话的 LLM token 消耗，防止上下文溢出。

**两种会话模式**：
- **storage（持久会话）**：消息存入 SQLite，支持历史回溯、归档、compact。默认模式
- **ephemeral（临时会话）**：消息仅存内存，关闭对话后丢失。适合快速问答

**Token 管理（仅 storage 模式）**：
- 系统追踪每个会话的累计 LLM token 消耗
- 超过阈值（默认 100k tokens，可配置）时提醒用户执行 compact
- 用户可开启 `auto_compact`：达到阈值自动触发 compact，无需手动操作
- **Compact 行为**：Group Ring 将历史对话压缩为摘要（summary），替换原始消息作为上下文输入。前端展示"正在压缩对话上下文..."提示。原始消息仍保留在 messages 表中供历史回溯，但不再喂给 LLM

### 2.10 通知系统

**描述**：Ring 内的事件通知机制。

**通知来源**：
- PR 状态变更（新 PR、合并、拒绝）
- 成员变更（新成员加入、角色调整、成员移除）
- Session 邀请

**推送方式**：
- 在线用户：WebSocket 实时推送
- 离线用户：通知缓存到本地 SQLite（`notifications` 表），下次启动前端展示未读通知列表

### 2.11 Ring 生命周期

- **active**：正常运行（Ring 创建后始终为 active，无归档冻结机制）
- Ring 的内容归档（对话→图谱节点+Markdown+Git commit）是持续性操作，不冻结 Ring 本身

### 2.12 Session 多人讨论

**描述**：Ring 内的多人实时讨论空间，区别于 Ring 级的仓库同步邀请。

**两层邀请机制**：

| 层级 | 目的 | 邀请范围 | 鉴权方式 | 数据同步 |
|------|------|---------|---------|---------|
| Ring 级 | 加入 Ring，获得仓库完整数据 | 任何人（通过 token） | API Key + invite token | Git clone/push/pull |
| Session 级 | 加入具体讨论，实时协作 | 仅 Ring 内已有成员 | Ring 成员身份验证 | 创建者后端 WebSocket 中转 |

**功能点**：
- Ring 内有权限的成员可创建 Session 并邀请其他 Ring 成员
- **同一个 Ring 同一时刻只能有一个活跃 Session**
- 创建 Session 必须选择预设场景（决定 Session Ring 的行为）：
  - `discussion`（自由讨论）：多人自由聊天，Session Ring 作为基础讨论助手
  - `deep_research`（深度调研）：跨源聚合 + 报告生成
  - `meeting_archive`（会议归档）：结构化提取 + 归档推荐
  - `learning_center`（学习中心）：知识解读 + 概念提取
- 所有参与者共享一个 Group Ring 实例，AI 回复对所有人可见
- 消息通过创建者后端 WebSocket hub 中转（不经过 GitLab）
- Session owner 离线时 Session 暂停，参与者无法发消息；owner 重连后自动恢复
- 离线成员重连后自动补发缺失消息（基于 seq_num）
- Session owner 可动态开关归档能力
- 归档开启后，仅 session owner 可触发归档操作（走 Ring 标准归档流程）
- Session 生命周期由 session owner 管理（关闭/删除/重新打开）
- 关闭的 session 保留聊天记录在创建者后端 SQLite，可随时重新打开

## 3. 非功能需求

### 3.1 性能

- 图谱渲染支持 100+ 节点不卡顿
- Git 操作（commit/push/pull）在 10 秒内完成
- AI 响应采用流式输出

### 3.2 安全

- Git 凭证加密存储
- 敏感信息隐私过滤（可配置规则）
- LLM API Key 本地加密存储

### 3.3 可用性

- 创建者机器在线时 Ring 可完整使用
- 成员本地有 Git 仓库克隆，可离线查看归档内容
- 新用户引导流程（Super Ring 辅助）
- **通知系统**：PR 状态变更、成员变更等通过 WebSocket 实时推送。用户离线时通知缓存到 SQLite，下次启动展示未读通知列表
- **Session 暂停机制**：Session owner 离线时 Session 暂停，所有参与者无法发消息。Owner 重连后自动恢复

### 3.4 可扩展性

- 工作流系统预留扩展能力（当前不开放自定义）
- 工具栏预留第三方工具接入空间
- 图谱模板支持用户自定义

## 4. 角色权限与权限模型

### 4.0 层级权限架构

Ring 采用层级权限管理机制。创建者对资源拥有完全权限，邀请进来的人需要在邀请时配置具体权限。Session 同理。

```
层级 1: Ring Hub（用户级）
  → 用户对自己机器上的所有资源拥有完全访问权
  → Super Ring 不受 Ring 角色权限限制，可只读访问本机所有 Ring 内容

层级 2: Ring（群组级）
  → Ring 创建者拥有完全权限
  → 邀请成员时，创建者配置成员权限（角色 + 具体操作权限）
  → 成员权限可在后续调整

层级 3: Session（讨论级）
  → Session 创建者拥有 session 完全权限
  → 但：创建 Session 本身需要 Ring 内的权限
  → 邀请 Ring 成员加入 session
```

#### 4.0.1 三层 AI 权限概览

| AI 层级 | 数据访问 | 写入能力 | 触发场景 |
|---------|---------|---------|---------|
| Super Ring（Hub 级） | 不受 Ring 角色限制，按需只读本机所有 Ring 内容 | 无（只读不写） | Ring Hub 页面 |
| Group Ring（Ring 级） | 读写本 Ring 图谱和归档 | 图谱操作 + 归档 + Git | 进入 Ring 空间后默认激活 |
| Session Ring（Session 级） | 继承 Group Ring 数据（只读） | 无（归档操作由 session owner 触发） | 多人 Session 激活时 |

### 4.1 角色定义

| 角色 | 描述 | 来源 |
|------|------|------|
| 创建者 | Ring 的创建人，拥有最高权限 | 创建 Ring 时自动获得 |
| 管理员 | 由创建者指定的协管者 | 创建者手动指定 |
| 成员 | 被邀请加入 Ring 的团队成员 | 通过邀请链接加入 |
| 只读 | 只能查看内容的旁观者 | 创建者/管理员手动设置 |

### 4.2 权限矩阵

| 操作 | 创建者 | 管理员 | 成员 | 只读 |
|------|--------|--------|------|------|
| 查看 Ring 信息 | ✅ | ✅ | ✅ | ✅ |
| 查看图谱和归档内容 | ✅ | ✅ | ✅ | ✅ |
| 和 Group Ring 对话 | ✅ | ✅ | ✅ | ❌ |
| 使用工具（会议归档/学习中心/深度调研） | ✅ | ✅ | ✅ | ❌ |
| Export 对话内容 | ✅ | ✅ | ✅ | ❌ |
| 手动归档（直接 commit） | ✅ | ✅ | ❌ | ❌ |
| 提交 PR（归档请求） | ✅ | ✅ | ✅ | ❌ |
| 审核 PR（合并/拒绝） | ✅ | ✅ | ❌ | ❌ |
| 查看其他成员的 PR | ✅ | ✅ | 仅自己的 | ❌ |
| 创建 Session（多人讨论） | ✅ | ✅ | 需创建者授权 | ❌ |
| 管理 Ring 成员（邀请/移除/角色调整） | ✅ | ❌ | ❌ | ❌ |
| 编辑 .ring/role.md 和 .ring/conventions.md | ✅ | ✅ | ❌ | ❌ |
| 修改蓝图模板 | ✅ | ❌ | ❌ | ❌ |

> **创建 Session 权限**：创建者和管理员可直接创建 Session；普通成员需要创建者预先授权。授权为永久授权（一直有效，直到创建者主动撤销）。被授权成员可以创建和关闭 Session，一次只能有一个活跃 Session。

> **PR 审核队列**：成员提交归档 PR 后进入串行审核队列，逐个审核避免 graph.json 冲突。冲突时打回给提交成员（关闭 MR + 通知），成员 pull 最新后重新提交。

> **.ring/ 写入权限**：`.ring/` 目录下所有文档（包括 role.md、conventions.md 及 AI 自动维护的 4 个文档），只有创建者和管理员可以写入（直接 commit）。成员完全只读，不可编辑不可 PR。成员想修改约定 → 向创建者/管理员提出。

### 4.3 交互模式

权限通过三种交互模式控制，决定 Group Ring 的自主权。

#### 4.3.1 日常对话模式

| 属性 | 值 |
|------|---|
| 触发方式 | 进入 Ring 后默认状态 |
| AI 权限 | 只读 — 可查询图谱和归档内容 |
| 允许操作 | 问答、聊天、调用工具查看结果 |
| 禁止操作 | 修改图谱、创建节点、Git 操作 |
| Git 操作 | 无 |
| 额外能力 | 可点击 export 按钮触发归档流程 |

#### 4.3.2 手动归档模式

| 属性 | 值 |
|------|---|
| 触发方式 | 用户说"归档"/"保存"/"记录到图谱"，或点击 export 按钮，或 AI 主动推荐 |
| AI 权限 | 推荐 — 可分析内容并推荐图谱操作 |
| 允许操作 | AI 推荐节点位置，用户确认后执行 |
| 确认要求 | 每个图谱操作都需要用户明确确认 |
| Git 操作 | 创建者/管理员：直接 commit；成员：提交 PR |

#### 4.3.3 Auto 模式

| 属性 | 值 |
|------|---|
| 触发方式 | 用户点击"Auto"按钮 |
| AI 权限 | 完全开放 — 读写图谱、生成 Markdown |
| 允许操作 | AI 自主判断内容是否值得归档并自动执行 |
| 确认要求 | 不需要用户逐个确认 |
| Git 操作（创建者/管理员） | AI 自动 commit |
| Git 操作（普通成员） | 批量标记推荐内容，用户一次性确认后合并成一个 PR |
| 退出方式 | 用户再次点击"Auto"按钮退出 |

### 4.4 邀请机制

#### 4.4.1 两种邀请链接

| 类型 | 加入方式 | token_id 分配 | 使用场景 |
|------|---------|-------------|---------|
| 开放链接（open） | 点链接直接加入 | 自动递增分配 | 团队内部快速拉人 |
| 审核链接（audit） | 点链接 → 提交申请 → 创建者审批 | 审批通过后分配 | 需要确认身份的邀请 |

#### 4.4.2 Token 规则

- Token 为一次性或多次（`max_uses`，开放链接可设为 0 表示不限）
- 格式：`base64url(random 32 bytes)`，不可猜测
- 默认有效期 24 小时，创建者可自定义
- 创建者可撤销未使用的 token（设置 `revoked_at`）
- 创建者可批量生成多个 token 分发给不同人
- 可选设 `max_members`（Ring 最大人数上限，防止链接泄露）

#### 4.4.3 生成邀请

1. 创建者在 Ring 空间点击"邀请"按钮
2. 选择链接类型（开放 / 审核）
3. 配置参数（角色、有效期、最大使用次数、最大人数）
4. 系统生成邀请链接：`http://{创建者内网IP}:7420/ring/join?token=xxx`
5. 创建者通过公司通讯工具发送链接

#### 4.4.4 加入流程（开放链接）

1. 被邀请人点击链接
2. 引导页检测本地 Ring 后端
3. 未安装 → 显示安装指引 → 安装后点击"继续加入" → 跳转本地 join URL
4. 已安装或跳转后 → 本地后端检查 Setup 状态
5. 未 Setup → 先走 Setup（display_name + LLM + GitLab）→ 完成后自动 join
6. 已 Setup → 直接 join
7. 输入 display_name → clone 仓库 → 分配 token_id → 加入 Ring

#### 4.4.5 加入流程（审核链接）

1. 被邀请人点击链接 → 看到 Ring 名称 + 成员列表
2. 输入 display_name + 申请理由
3. 创建者收到通知 → 审批
4. 批准 → 分配 token_id → clone 仓库 → 通知申请人
5. 拒绝 → 通知申请人（附理由）

#### 4.4.6 角色变更

- 创建者可将成员提升为管理员
- 创建者可将管理员降级为成员
- 创建者可将成员设为只读
- 创建者可移除成员
- 管理员不能变更角色

### 4.5 Session 级权限

> Session 是 Ring 内的多人实时讨论会话。Session 有独立的权限控制，与 Ring 级权限正交。

#### 4.5.1 Session 角色

| 角色 | 描述 | 来源 |
|------|------|------|
| Session Owner | Session 创建者，拥有 session 管理权限 | 创建 Session 时自动获得 |
| Participant | Session 参与者，可收发消息和查看 AI 回复 | 被 session owner 邀请 |

#### 4.5.2 Session 权限矩阵

| 操作 | Session Owner | Participant | 只读成员（旁听者） |
|------|--------------|-------------|-----------------|
| 查看消息和 AI 回复 | ✅ | ✅ | ✅ |
| 发送消息 | ✅ | ✅ | ❌ |
| 邀请其他 Ring 成员加入 session | ✅ | ❌ | ❌ |
| 移除 participant | ✅ | ❌ | ❌ |
| 开关归档能力 | ✅ | ❌ | ❌ |
| 触发归档操作（需归档已开启） | ✅ | ❌ | ❌ |
| 关闭 session | ✅ | ❌ | ❌ |
| 重新打开已关闭的 session | ✅ | ❌ | ❌ |
| 删除 session | ✅ | ❌ | ❌ |
| 主动离开 session | ✅ | ✅ | ✅ |

#### 4.5.3 Session 鉴权

- **加入鉴权**：被邀请者必须是 Ring 的已有成员（任意角色），由创建者后端验证
- **WebSocket 连接鉴权**：连接 session WebSocket 频道时需提供 Ring 成员身份 token
- **归档鉴权**：session 归档操作走 Ring 内角色权限（创建者/管理员直接 commit，成员提交 PR）

#### 4.5.4 Session 与 Ring 权限关系

```
Ring 级权限
├── 决定：能否进入 Ring 空间
├── 决定：能否创建 Session（创建者/管理员可创建，成员需授权）
├── 决定：归档时的 Git 操作权限（直接 commit vs 提交 PR）
├── 决定：能否被邀请进 Session（必须是 Ring 成员）
└── 决定：成员被移除时的 Session 处理

Session 级权限
├── 决定：session 内的管理操作（invite/close/delete）
├── 决定：谁能触发归档（仅 session owner）
└── 决定：归档开关（仅 session owner）
```

#### 4.5.5 成员移除时的 Session 处理

当 Ring 创建者移除一个成员时，需处理该成员参与的活跃 Session：

| 被移除者在 Session 中的角色 | 处理方式 |
|--------------------------|---------|
| Session Owner | 创建者必须先指定继承者（转移 session ownership），才能移除该成员 |
| Participant | 保留该成员的所有历史消息，通过 WebSocket 踢出 session（`session_member_kicked`），该成员立即无法继续发送消息 |

#### 4.5.6 Session 暂停机制

当 Session owner 离线时：

- 后端推送 `session_paused` 事件给所有参与者
- 所有参与者无法发消息，Session 暂停
- Session owner 重连后推送 `session_resumed` 事件
- 所有参与者可继续发消息
- **不设临时接管机制**：消息始终存储在 Session owner 后端的 SQLite 中，避免多端消息合并复杂度

## 6. 用户流程

### 6.1 Ring 生命周期

```
创建 Ring → 蓝图构建 → 日常使用 → 持续演化
```

#### 6.1.1 创建 Ring

1. 用户在 Ring Hub 点击"创建 Ring"
2. 填写 Ring 名称（如"产品竞品分析组"）
3. 填写 AI 角色描述（如"你是一个产品分析专家，帮助团队进行竞品研究"）→ 初始化 `.ring/role.md`
4. 关联 GitLab 仓库：
   - 输入已有仓库地址，或
   - 点击"自动创建"（可选填 `namespace`，默认用个人 namespace）
5. 凭证复用全局 GitLab 配置（Setup 时已配置）
6. 后端初始化仓库 → push 初始 commit
7. 进入蓝图构建阶段

#### 6.1.2 蓝图构建

**入口页面展示模板卡片列表**，用户可以选择：

**快速路径**：
1. 用户浏览预设模板（产品研究、项目管理、学习笔记、技术文档、空白）
2. 点击模板卡片 → **预览图谱结构**（节点+边 D3.js 可视化）
3. 点击"使用此模板" → 确认蓝图 → 建立 → 进入 Ring 空间

**深度路径**：
1. 用户点击"自定义"或"从零开始"
2. Group Ring 使用蓝图 prompt + role.md 叠加作为 system prompt，引导构建
3. 通过不限轮数的对话，和用户反复确认：
   - 需要几个图谱（默认上限 3，过高提醒资源消耗）
   - 每个图谱的主题和顶层分类
   - 初始节点结构
4. 每次调整后展示可视化预览
5. 用户点击"确认蓝图" → 建立
6. 进入 Ring 空间，开始日常使用

#### 6.1.3 日常使用

Ring 进入持续演化阶段，成员在三种模式间切换使用。

### 6.2 三种使用模式流程

#### 6.2.1 日常对话模式（默认）

**触发**：进入 Ring 后默认状态

**流程**：
```
用户提问/聊天
  → Group Ring 响应（查询图谱、归档内容，回答问题）
  → 不产生任何 Git 操作
  → 对话内容仅存在于会话中
```

**Export 能力**：
- 用户可在对话中随时点击 export 按钮
- 将当前对话片段标记为"值得归档"
- 触发手动归档流程

#### 6.2.2 手动归档模式

**触发**：
- 用户在对话中说"归档"/"保存"/"记录到图谱"
- 用户点击 export 按钮
- Group Ring 主动推荐"是否归档到图谱"（工具产出后）

**流程**：
```
标记归档
  → 后端自动 git pull（确保本地图谱最新）
  → Group Ring 分析内容，识别关键信息
  → Group Ring 推荐图谱操作（"我建议创建新节点 XX" 或 "挂载到节点 YY 下"）
  → 展示推荐预览
  → 用户确认
  → 生成 Markdown 文件 + 更新 graph.json
  → 创建者/管理员：直接 commit + push
  → 成员：创建分支 → commit → push → GitLab API 创建 MR → 进入审核队列
  → 所有成员自动 pull 最新内容
```

**PR 审核队列**：
```
成员提交归档 PR
  → 进入审核队列（前端显示队列位置）
  → 创建者逐个审核（串行，避免 graph.json 冲突）
  → 无冲突：合并 → 所有成员 pull
  → 有冲突：打回（关闭 MR + 通知成员）
  → 成员收到打回通知 → pull 最新 → 重新提交
```

#### 6.2.3 Auto 模式

**触发**：用户点击"Auto"按钮

**流程**：
```
用户上传文档 / 对话 / 使用工具
  → AI 自动判断内容是否值得归档（基于 LLM 语义判断：内容包含决策/结论/知识点）
  → AI 自动执行归档（创建/更新节点，生成 Markdown，commit）
  → 不需要用户逐个确认
  → 用户可随时退出 Auto 模式
```

**边界**：
- 闲聊内容不归档（"今天天气真好"）
- 上传文件自动归档
- 对话基于语义判断是否归档
- 误归档可通过多种方式修正（图谱编辑、对话修正、Git 回滚）

### 6.3 成员加入流程

#### 6.3.1 开放链接加入

```
创建者生成开放链接
  → http://{创建者内网IP}:7420/join?token=xxx
  → 被邀请人点击链接
  → 创建者的 ring-server 服务安装导航页（去中心化）：
     ├── 页面显示：Ring 名称 + 描述 + 成员数
     ├── 自动检测访问者 OS（User-Agent）
     │   ├── Windows → 高亮 Windows 下载按钮
     │   ├── Linux/WSL → 高亮 Linux 下载按钮
     │   └── macOS → 高亮 macOS 下载按钮
     ├── 下载链接指向 GitHub Releases：
     │   https://github.com/{owner}/ring/releases/latest/download/{filename}
     ├── 已安装 Ring 的用户：直接点击"继续加入"
     └── 未安装用户：三步引导
         1. 下载对应平台二进制文件
         2. 解压并运行 ring-server
         3. 点击"继续加入"按钮
  → "继续加入"跳转 http://localhost:7420/join?token=xxx&creator_ip={创建者IP}
  → 本地后端处理：
     ├── 未 Setup → 先走 Setup 向导 → 完成后自动 join
     └── 已 Setup → 直接走 join 流程
  → 输入 display_name
  → Ring 自动从 GitLab clone 仓库到本地
  → 分配 token_id（自增长）
  → 加载图谱和归档内容
  → 同步其他成员名称列表
  → 加入 Ring，获得对应角色权限
```

> **去中心化安装**：安装导航页由分享链接的用户 ring-server 提供，无需中央安装服务器。二进制文件统一从 GitHub Releases 下载。

#### 6.3.2 审核链接加入

```
创建者生成审核链接
  → 被邀请人点击链接 → 创建者的 ring-server 服务安装导航页（同 6.3.1）
  → 安装并"继续加入"后看到 Ring 名称 + 成员列表
  → 输入 display_name + 申请理由
  → 创建者收到通知："xxx 请求加入 Ring"
  → 创建者看到申请人名字 + 现有成员列表
  → 批准 / 拒绝
  → 批准后：分配 token_id，自动 clone 仓库，通知申请人
  → 拒绝后：通知申请人（附理由）
```

### 6.4 PR 审核流程（创建者视角）

```
成员在对话中标记归档
  → 后端自动：创建本地分支 → 生成 Markdown + 更新 graph.json → commit → push
  → 后端通过 GitLab API 创建 MR
  → 创建者在 Ring 归档视图看到 PR 通知
  → 创建者点击"查看 Diff" → 弹出并排对比视图
  → 创建者点击"合并" → GitLab API 合并 MR → 所有成员自动 pull
  → 或创建者点击"拒绝" → GitLab API 关闭 MR
```

### 6.5 图谱生长流程

#### 6.5.1 新内容产生

```
用户在对话中讨论新主题 / 上传新文件 / 使用工具
  → AI 分析内容
  → 匹配蓝图中某个图谱的某个大类
  → 建议：
    a) 归入已有子节点
    b) 在已有大类下创建新子节点
    c) 建议新增顶层大类（需用户确认，因为这改变了蓝图结构）
```

#### 6.5.2 节点创建

```
AI 建议"创建新节点 XX"
  → 用户确认（手动模式）/ AI 自动执行（Auto 模式）
  → 生成节点数据（graph.json 更新）
  → 生成对应的 Markdown 文件
  → Git 操作（commit 或 PR）
```

#### 6.5.3 边创建

```
Group Ring 识别两个节点之间的关系
  → 建议"节点 A 和节点 B 存在'依赖'关系"
  → 用户确认 / AI 自动执行
  → 更新 graph.json
  → Git 操作
```

### 6.6 Session 多人讨论流程

#### 6.6.1 创建 Session

```
Session 创建者（需有 Ring 内的 Session 创建权限）
  → 检查：该 Ring 是否已有活跃 Session（一次只能有一个）
  → 在 Ring 空间点击"新建讨论"
  → 选择预设场景（必选）：
     ├── discussion（自由讨论）：多人自由聊天，基础讨论助手
     ├── deep_research（深度调研）：跨源聚合 + 报告生成
     ├── meeting_archive（会议归档）：结构化提取 + 归档推荐
     └── learning_center（学习中心）：知识解读 + 概念提取
  → 填写 Session 标题（如"竞品 A 深度讨论"）
  → 选择是否开启归档（可后续动态切换）
  → 选择邀请哪些 Ring 成员
  → 系统创建 Session Ring（基于预设场景配置）
  → 创建者成为 session owner
  → 被邀请成员收到 WebSocket 通知
```

> 预设场景决定 Session Ring 的行为和能力边界。例如选择"深度调研"时，Session Ring 会主动调用搜索、爬取、聚合等工具。

#### 6.6.2 Session 内讨论

```
成员发消息
  → 消息发送到创建者后端（WebSocket）
  → 创建者后端存入 session_messages（带 seq_num）
  → 广播给所有 session 成员（包括发送者）
  → Group Ring（共享实例）响应
  → AI 回复也广播给所有成员
```

**特点**：
- 所有成员共享一个 Group Ring 实例
- AI 回复对所有人可见
- 消息通过创建者后端中转
- 离线成员重连后自动补发缺失消息（基于 seq_num）

#### 6.6.3 Session 归档（可选）

```
Session owner 开启归档（动态切换）
  → session 内出现"归档"按钮
  → Session owner 选择消息片段 → 触发归档
  → 走标准归档流程（AI 分析 → 推荐图谱操作 → 确认 → Git commit/PR）
  → 归档结果写入 Ring 的知识图谱
```

#### 6.6.4 Session 生命周期

```
创建 Session
  → 活跃讨论（active）
  → Session owner 关闭 Session（closed）
     → 聊天记录保留在创建者后端 SQLite
     → Session owner 可随时重新打开
  → 或 Session owner 删除 Session（deleted）
     → 所有记录清除，不可恢复
```

#### 6.6.5 成员离线处理

```
成员网络中断
  → 创建者后端继续缓存该 session 的消息
  → 成员重连
  → 客户端发送最后收到的 seq_num
  → 创建者后端返回 seq_num 之后的所有消息
  → 成员看到完整的离线期间讨论
```

#### 6.6.6 Session owner 离线处理

```
Session owner 离线
  → 创建者后端推送 session_paused 事件给所有参与者
  → 所有参与者无法发消息（Session 暂停）
  → Session owner 重连
  → 创建者后端推送 session_resumed 事件
  → 所有参与者可继续发消息
```

### 6.7 导出流程

#### 6.7.1 导出图谱图片

```
用户在图谱视图中点击"导出"按钮
  → 选择格式（PNG / SVG / PDF）
  → 前端通过 D3.js 渲染静态快照
  → 下载文件
```

#### 6.7.2 导出 Markdown / 对话 / Session 记录

```
用户在对应视图中点击"导出"
  → 选择格式（Markdown / PDF）
  → 后端生成文件
  → 下载
```

#### 6.7.3 生成 AI 结构化报告

```
用户选择一个或多个图谱节点
  → 点击"生成报告"
  → 填写报告主题
  → Group Ring 基于节点内容生成结构化报告
  → 用户预览 → 选择导出格式（Markdown / PDF）
```

#### 6.7.4 整 Ring 数据备份

```
用户在 Ring 设置中点击"备份数据"
  → 后端打包 graph.json + Markdown + 元数据 + assets
  → 生成 .tar.gz 文件
  → 下载
```

### 6.8 图谱修正流程

```
场景：Group Ring 创建了错误的节点/边，或归档了不该归档的内容

修正方式（二选一）：

1. 对话中指示 Group Ring
   → 用户说"删除刚才那个节点" 或 "把节点 A 的内容改一下"
   → Group Ring 执行修正
   → 变更生成 Git commit/PR

2. Git 回滚
   → 在归档视图的提交历史中找到错误 commit
   → 执行 revert
   → 图谱恢复到之前的状态
```

> **图谱可视化**：支持展开/折叠节点（查看或隐藏子节点），支持缩放、平移、高亮。不支持在可视化界面上直接编辑。
