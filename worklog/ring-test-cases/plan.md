# Ring Test Cases Plan

## 总体思路

先从 API 与现有测试中抽取功能边界，再以人工测试为目标组织测试内容。测试文档按功能模块拆分，避免一个超大文档难以执行和维护。

## 阶段划分

1. 环境与功能盘点
   - 阅读 README、API 文档、路由注册和现有测试。
   - 确认测试范围为全功能均衡。

2. 工作记录初始化
   - 创建 `worklog/ring-test-cases/`。
   - 初始化 `spec.md`、`plan.md`、`status.md`。

3. 测试目录生成
   - 创建根目录 `test/`。
   - 按 12 个功能域创建子目录。

4. 测试内容编写
   - 编写 `test/README.md` 与 `test/test-data.md`。
   - 为每个功能域编写 `cases.md`。
   - 每个用例包含前置条件、输入、步骤、期望输出和问题记录。

5. 验证
   - 检查文件是否完整。
   - 检查主要 API/功能是否映射到测试用例。

## 里程碑

- M1：worklog 初始化完成。
- M2：测试目录结构完成。
- M3：全功能人工测试用例完成。
- M4：文档完整性检查完成。

## 验证方式

- 使用文件列表确认所有目标文档存在。
- 抽查关键路径：Setup、Ring、成员邀请、Session、聊天、图谱、归档、Super、Self、导出。
- 确认文档没有要求测试人员反查代码才能执行。

## 风险与依赖

- 部分 AI 输出不稳定，人工测试只验证结构化事件、状态、可观察副作用和内容合理性。
- WebSocket 测试需要浏览器或 WebSocket 客户端辅助。
- PDF/PNG 导出依赖运行环境能力，若失败需记录错误详情。

## 待确认事项
